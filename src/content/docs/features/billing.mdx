四种支付服务商(Stripe / Waffo / Creem / PayPal)可任意组合启停,档位与商品 ID 全部收敛在一个配置文件里,webhook 幂等落库、套餐门控、扣款失败(dunning)站内提示。本页讲**档位配置**、**支付商开关**、**webhook 处理**与**权益模型**。

## 一个文件决定全部:`features/billing/plans.ts`

档位、价格、功能点、以及**每家支付服务商在每个周期上的商品 ID**,都写在这一个纯数据模块里。改完这一处,定价页、结账页、服务端商品校验、webhook 档位反查全部同步——组件里没有任何硬编码的档位或价格。

```ts
export const planTiers = [
  {
    id: 'pro',
    name: { en: 'Pro', zh: 'Pro' },
    summary: { ... },
    featured: true,
    monthly: { amountUsd: 9,  productIds: { stripe: 'price_…', waffo: 'PROD_…', creem: 'prod_…', paypal: 'P-…' } },
    yearly:  { amountUsd: 90, productIds: { ... } },
    bullets: [
      { text: { en: 'Everything in the Free tier', zh: '免费版的全部功能' }, enabled: true },
      { text: { en: 'SSO / SAML + audit log', zh: 'SSO / SAML + 审计日志' }, enabled: false },
    ],
  },
] as const satisfies readonly PlanTier[]
```

几个约定:

- **`productIds` 的空串 = 该服务商在这个档位/周期上没有商品**,结账页不会出现它的按钮。这不是错误。
- **PayPal 的商品 ID 必须以 `P-` 开头**(订阅计划 ID)。不带前缀会让适配器静默降级成一次性订单并被 PayPal 拒绝,所以 `startCheckout` 显式校验并报错。
- **`bullets[].enabled: false` = 尚未上线**。定价页灰显展示;**结账页把它们单独列在「已公布,尚未上线」区块**,不混进「这笔订单包含」——订单页不该承诺还没上线的东西。
- 旧的 `STRIPE_PRICE_PRO_*` 变量已移除。商品 ID 本来就要下发到收银台,不是密钥;和档位放在一起才能一眼看清「谁能在哪儿买什么」。

## 支付服务商与开关

`BILLING_PROVIDERS` 是唯一的启停开关,非密钥 `wrangler.jsonc#vars`:

```
BILLING_PROVIDERS=stripe,waffo
```

- **未设置或为空 = 四家全开**,但每家仍各自受密钥门控。这样「配了 Creem 密钥却忘了配开关」不会静默失效;真正关闭某一家,就把它的 id 从列表里删掉。
- 注意区分两个概念:定价页的 **logo 条**只反映开关(「我们接受哪些支付方式」),而**结账页的按钮**是开关 ∩ 密钥 ∩ 商品 ID 三者交集(「现在点什么真能付」)。所以全新克隆的部署会在 logo 条上看到四家、而在结账页看到零家——这是设计如此,填完 `plans.ts` 商品 ID 后即一致。
- 一个服务商要真正出现在结账页,必须同时满足三条:①在 `BILLING_PROVIDERS` 里 ②该家密钥齐全 ③`plans.ts` 里该档该周期的 `productIds[id]` 非空。
- 判定只有一处:`providers/registry.ts` 的 `resolvePurchase(env, tier, interval, provider)`。**结账页渲染按钮和 `startCheckout` 建会话调用的是同一个函数**,所以「页面上能点的按钮」和「点了真能付」不可能不一致——包括 PayPal 的 `P-` 前缀校验,它同时作用在两条路径上(否则页面会画出一个必然报错的按钮)。`startCheckout` 仍是安全边界:客户端传来的 `provider` 会被重新判定一次。

| 服务商 | 所需变量(全部 `wrangler secret put`) | 非密钥变量 |
|---|---|---|
| Stripe | `STRIPE_SECRET_KEY`、`STRIPE_WEBHOOK_SECRET` | — |
| Waffo Pancake | `WAFFO_MERCHANT_ID`、`WAFFO_PRIVATE_KEY`(或 `WAFFO_PRIVATE_KEY_BASE64`)、`WAFFO_WEBHOOK_PUBLIC_KEY` | `WAFFO_ENV` |
| Creem | `CREEM_API_KEY`、`CREEM_WEBHOOK_SECRET` | `CREEM_ENV` |
| PayPal | `PAYPAL_CLIENT_ID`、`PAYPAL_CLIENT_SECRET`、`PAYPAL_WEBHOOK_ID` | `PAYPAL_ENV` |

`CREEM_ENV` / `PAYPAL_ENV` / `WAFFO_ENV` **默认沙箱**,上生产需显式设成 `live`。

`env-validate.ts` 在启动时对两种情况给出提示:

- **在 `BILLING_PROVIDERS` 里但密钥不全** → warn。这类错误的症状是「按钮不见了」而不是报错,不主动提示就只能等第一个付不了款的客户。
- **密钥齐全但 `plans.ts` 里一个商品 ID 都没有** → warn,并且措辞很重。因为这是唯一会导致**「顾客付了钱却什么都没拿到」**的故障:webhook 验签正常、定价页正常渲染,只是 `tierForProduct` 反查不出档位。webhook 侧还会再打一条 `console.error` 点名是哪个商品 ID 对不上。

半套凭据(只配了 key 没配 secret)是**硬错误**,与 OAuth 的处理一致——但**只在 `BILLING_PROVIDERS` 列出了该家时才判定**。开关未设等于「四家全开、各自受密钥门控」,无条件判定会让一个几个月前随手设过 `CREEM_API_KEY`、从未启用 Creem 的部署直接启动崩溃,正好违反本仓库的优雅降级约定。

### Webhook 回调地址

每家一个路由(签名头在各自边界处理):

| 服务商 | 回调 URL | 签名头 |
|---|---|---|
| Stripe | `/api/webhooks/stripe` | `stripe-signature` |
| Waffo | `/api/webhooks/waffo` | `x-waffo-signature` |
| Creem | `/api/webhooks/creem` | `creem-signature` |
| PayPal | `/api/webhooks/paypal` | 5 个 `paypal-*` 头 |

本地开发把公网隧道指向 Vite dev server 即可(例如 `https://<tunnel>/api/webhooks/creem`)。

验签方式各不相同:

- **Waffo / Creem** 覆盖**原始字节**,所以路由必须先 `await request.text()` 再做任何解析。任何「先 parse 再序列化」的写法都会让签名校验假性失败——`webhook-handler.ts` 把这个顺序收敛到一处。
- **PayPal** 的 RSA 签名需要 X.509 证书链,而 Workers 没有 `crypto.createVerify`,因此改为把投递转发到 PayPal 官方的 `verify-webhook-signature` 接口由它裁决。**该接口 5xx 时路由回 502**(让 PayPal 重投),签名判定失败回 400——两者混为一谈会静默丢掉真实付款事件。
- **Stripe** 的路由是唯一一个手写的:赞助和产品计费共用它,验签一次后分流。

### 归属用户:三家没有 customer id

只有 Stripe 允许预创建 customer。Waffo / Creem / PayPal 的 webhook 靠下单时写进 `metadata` 的 `userId` 回传(`applyDomainEvent` 优先按 `userId` 定位订阅行,其次按 `customerId`,都没有则忽略)。

`subscription.provider` 记录该行属于哪一家,**webhook 到达时会核对**:不属于本厂商的事件一律忽略。否则用户在 waffo 重新付费后,一条几小时前迟到的旧 Stripe 事件会把新订阅降级。

幂等键写作 `${providerId}:${eventId}`,四家的事件 ID 因此不会互相吞掉重投。

## 取消订阅:我们只写意图,厂商 webhook 写终态

点击「取消订阅」后发生的事,顺序是有讲究的:

1. **先在厂商侧取消**。失败就抛错,不留「本地说在取消中、厂商根本没收到」的假状态。
2. **本地只写 `canceling`**,绝不写 `canceled` / 降级 free。
3. **页面立即显示「取消中」**,并说明「正在等待支付服务商确认,刷新本页可查看最终状态」。
4. **厂商 webhook 到达**后,由 `applyDomainEvent` 写入真正的终态。

为什么本地不直接写终态?因为只有厂商知道这次取消**是否真的生效**。我们先写终态,就会和厂商状态分叉——用户看到「已取消」,厂商其实还在扣费。

那为什么还要写一次 `canceling`?因为刷新页面时它比 `active` 诚实:用户点了取消、厂商还没回 webhook 时,行上写着 `active` 会让人以为没点上。

**已知取舍**:若 webhook 丢失(例如验签 400 这类不会被重投的情况),行会停在 `canceling`。这是刻意的——停在 `canceling` 用户看得见并会重试;停在 `active` 则会静默地继续扣费。

另外 **`canceling` 仍然算有效权益**:期末生效型厂商(Creem 的 scheduled_cancel、Stripe 的 `cancel_at_period_end`)表示「已付费周期结束前仍然可用」。如果把 `canceling` 排除在有效状态外,一个刚点了取消的用户会在周期结束前立刻失去已付费的权益。

## 权益模型(`entitlement.ts`)

`getEntitlement()` 返回 `Entitlement`:`{ plan, status, isActive, currentPeriodEnd, lifetime, paymentFailed, provider }`。

- `plan`:`free` | `pro` | `enterprise`。`isAtLeastTier(plan, 'pro')` 做门控(企业版天然过 Pro 门);`role === 'admin'` 直接放行。功能门控用 `hasProAccess(role, ent)`,计费 UI 保持用 `ent.plan` 反映真实订阅。
- `provider`:决定账户页显示「管理订阅」(Stripe 客户门户)还是「取消订阅」(其余三家站内取消),并按 `cancelMode` 提示**期末生效**还是**立即生效**——Creem 是期末,Waffo / PayPal 没有「期末取消」这个选项,当场生效。
- `lifetime`:一次性买断优先于一切 status。**当前 `startCheckout` 只开订阅模式**,所以一次性订单的 UI 入口还不存在;`lifetime` 列、`purchase.completed` / `purchase.refunded` 事件与对应逻辑保留着,是为存量数据和将来开放一次性商品准备的。⚠️ PayPal 的一次性分支目前**不可用**(`purchase.completed` 记的是 `related_ids.order_id`,而退款事件不带该字段,退款无法精确匹配),所以上架一次性商品前需要先补这条。
- `paymentFailed`:续费扣款失败的**站内信号**(见下文)。

## Webhook 处理

适配器把各厂商的事件归一成同一套领域事件(`subscription.upserted` / `subscription.deleted` / `purchase.completed` / `purchase.refunded` / `payment.failed` / `ignored`),落库时幂等(`processed_webhook_events` 去重)。档位不由事件自报,而是用**商品 ID 反查 `plans.ts`**(`tierForProduct`),所以客户端无法指定自己买了什么。

| 领域事件 | 处理 |
|---|---|
| `subscription.upserted` | upsert 订阅状态;`active/trialing` → 门控开;`canceling` → 保留权益并置 `cancel_at_period_end` |
| `subscription.deleted` | 降级 free |
| `purchase.completed` | 买断激活;先在厂商侧停掉在生效中的订阅,避免双扣费 |
| `purchase.refunded` | 按支付引用精确匹配后撤授权——同账户其他 charge 的退款与本次授权无关 |
| `payment.failed` | 置 `payment_failed_at`(站内 banner),触发 `onPaymentFailed` 钩子 |
| `ignored` | 200 且**不占幂等表**(否则账户上每个无关事件都永久留痕) |

厂商侧状态与事件的对应关系(容易踩的两处):**Waffo / Creem 的「取消中」是 upsert 而非 delete**(付费周期未结束);**Creem 的 `unpaid` 归 `payment.failed`** 而不是取消。

## 扣款失败(Dunning)

重试与催缴邮件**交给各自的厂商**——它们做得比手搓的好,而且零代码:在各自 Dashboard 开启智能重试与失败邮件。

模板只补厂商给不了的那一件事——**站内信号**:

- 收到 `payment.failed` → 订阅行置 `payment_failed_at`(`billing.server.ts`)。
- `resolveEntitlement` 据此暴露 `entitlement.paymentFailed`。
- 登录后的 app 顶部显示 `PaymentFailedBanner`,让用户更新支付方式。
- 扣款恢复(订阅回到 `active/trialing`)时 flag **自动清除**。

> 为什么不在 app 里发阶梯催缴邮件?那会和厂商能力重复、且节奏脆弱。分工后 **dunning 不需要 Cron**——这也是 Cron 在开源版被定性为「清理任务参考实现」而非计费基建的原因(见 [cf-gotchas](/docs/platform/cf-gotchas))。

## 扩展一家新服务商

1. 在 `providers/<id>.ts` 实现 `PaymentProvider`(`parseWebhook` 收到完整 headers,不必像某些实现那样把多个头打包成 JSON 信封);
2. 在 `providers/catalog.ts` 加一条元数据(显示名、logo、取消语义、所需密钥);
3. 在 `providers/registry.ts` 的 `getBillingProvider` 加一个 case,并在 `hasRequiredSecrets` 补密钥门控;
4. 建一个 `src/routes/api/webhooks/<id>.ts`,一行 `createWebhookHandler('<id>')`;
5. 在 `plans.ts` 填上该家商品 ID,在 `BILLING_PROVIDERS` 里加上 id。

UI 侧不需要任何改动:定价页 logo 条与结账页按钮都是从 `catalog.ts` 驱动的。
