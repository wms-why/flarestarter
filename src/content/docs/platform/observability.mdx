两项都是**可选**、互不影响:分析在 Cloudflare 侧开关,错误上报用 env 控制、留空即关闭。
加上可选的 Google Analytics 4(构建期开关,留空即不集成)。

## Cloudflare Web Analytics(零配置)

隐私友好、免费、零 cookie 的访问分析。

- **怎么开**:Dashboard → Analytics & Logs → Web Analytics 建一个站点并开启(保持默认的
  自动注入 / "Automatically inject" 开关打开即可)。
- **原理**:Cloudflare 在边缘把 beacon 脚本注入到 HTML 响应里,**应用侧不需要任何代码、
  也不需要任何环境变量**——本模板既不手动注入 beacon,也不读 token。
- **CSP**:生产环境的 CSP 已放行 `static.cloudflareinsights.com`(脚本)与
  `cloudflareinsights.com`(上报),因此边缘注入的 beacon 不会被 CSP 拦掉(见
  [安全文档](/docs/platform/security))。
- **没开**:Cloudflare 侧不启用就没有任何分析,应用无感知。
- **前提**:自动注入是 **zone 级**的——只有走该 zone 代理的自定义域名会被注入;直接访问
  `*.workers.dev` 地址不会有 beacon(统计也会随之缺失)。

## Google Analytics 4(`GA_MEASUREMENT_ID`)

需要 Google Ads 受众、关键事件(转化)或 GA4 级别的报表时再开。Cloudflare Web Analytics
已经覆盖了「流量 + 体验指标」这一层,两者可以并存。

- **怎么开**:GA4 后台 → 管理 → 数据流 → **Web** → 复制「衡量 ID」(形如 `G-XXXXXXXXXX`)。
- **在哪配**:**构建期**变量,不是运行时 env。写进 `.env`(本地,参考
  [`.env.example`](https://github.com/flarestarter/flarestarter/blob/main/.env.example))或 CI 的
  环境变量(生产),**不要**写进 `.dev.vars` / `wrangler secret`——Cloudflare 的 var 要等 worker
  跑起来才存在,那时产物早已定型,「没配就不集成」就落空了。
- **没配会怎样**:**打包不集成**。构建脚本(`vite.config.ts`)把 GA 加载器换成空实现,GA 代码
  根本不会进入模块图——产物里搜不到 `googletagmanager`,浏览器也不会向 Google 发一个请求;
  生产 CSP 里同样不会放行 Google 的域名(连「理论上能通」都不留)。
- **原理**:客户端组件(`src/features/analytics/`)在路由变化时上报 `page_view`。GA4 不认识 SPA
  路由,所以关掉自动上报(`send_page_view: false`),由应用自己发,避免首个页面被统计两次。
- **CSP**:开启后自动放行 `www.googletagmanager.com`(脚本)与
  `*.google-analytics.com` / `*.google.com` / `analytics.google.com`(上报),清单见
  `src/features/analytics/csp-hosts.ts`(依据 [Google 官方 CSP 指南](https://developers.google.com/tag-platform/security/guides/csp))。

### 范围与限制(诚实说明)

- **纯客户端**:浏览器直接上报。服务端事件(Measurement Protocol / Conversion API)模板**没有**
  封装——它需要 API secret、`client_id` 串联等,不是模板替你拍板的事。
- **没有接 CMP / Consent Mode**:模板不弹 cookie 横幅,也没实现 Consent Mode v2。在 EEA
  (含欧盟)用 GA4 时,Google 要求实现 Consent Mode v2 才能用广告受众;需要的话在
  `src/features/analytics/ga-loader.ts` 的 `gtag('config', …)` **之前**加一行
  `gtag('consent', 'default', { analytics_storage: 'denied', … })`,再接上你自己的 CMP
  (注意:不要把 GA 标签挡在横幅后面,否则会丢数据)。
- **IP**:GA4 会用 IP 推导国家/城市,但**不记录 IP 本身**;GA4 也没有旧版 UA 的「IP 匿名化」
  开关。另外 GA 会采集页面 URL 与标题,**别把 PII 放进 URL**。
- **域名**:GA4 不要求自定义域名,`*.workers.dev` 也能上报;但那会把流量拆成多个 hostname
  维度。另外注意 Cloudflare Web Analytics 的自动注入只在走 zone 代理的域名上生效。
- **缓存**:若之后给 HTML 加 `Cache-Control: public, no-transform`,Cloudflare 边缘的
  HTML 改写会失效(这主要影响 Web Analytics 的 beacon 注入)。

## Sentry 错误上报(`SENTRY_DSN`)

捕获 worker 端的**未处理异常 / promise rejection**(SSR、loader、server fn、API route)——也就是生产里你最看不见的那类错误。

- **怎么开**:在 [sentry.io](https://sentry.io) 建项目,拿 **DSN**,设进 `SENTRY_DSN`(生产用 `wrangler secret put SENTRY_DSN`)。
- **原理**:`src/worker.ts` 用 `@sentry/cloudflare` 的 `withSentry()` 包住 worker 入口。options 回调在**没有 DSN 时返回 `undefined`,Sentry 完全不初始化**(不是「初始化了但没 dsn」)。默认 `tracesSampleRate: 0`(仅错误、不采性能)、`sendDefaultPii: false`。
- **未配**:Sentry 不初始化,零开销。

### 范围与限制(诚实说明)

- **仅服务端**。浏览器端错误**未捕获**——需要的话新建客户端 entry + `@sentry/react`(会增大客户端 bundle)。
- **框架已处理的错误**(loader/render 报错走 `ErrorPage` 错误边界的那些)不会自动上报,因为它们没作为异常冒泡到 worker。需要的话在错误边界或对应位置手动 `Sentry.captureException`。
- `withSentry` 自动捕获的是**真正未处理**的异常与 rejection。

> 部署小坑:首次 `pnpm install` 后第一次 `pnpm dev`,Vite 因 lockfile 变化会重新优化依赖,可能出现一次性内存峰值导致进程被 kill——重启 `pnpm dev` 即正常。
